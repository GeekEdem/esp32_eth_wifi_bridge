# C3-програматор для WT32-ETH01

*[English](README.md)*

Прошивка для **ESP32-C3 SuperMini**, яка перетворює його на програматор і послідовний монітор WT32-ETH01:

- **Через Wi-Fi (RFC2217):** `esptool` / `idf.py` прошивають і читають лог WT32 як звичайний порт `rfc2217://c3prog.local:4000`. Швидкість і DTR/RTS передаються по мережі: RTS → EN, DTR → IO0, як на звичайному USB-UART з автоскиданням.
- **Через USB (запасний шлях):** USB C3 ↔ UART WT32 на фіксованих 115200. Бутлоадер — кнопкою або з веб-сторінки.
- **Веб-сторінка** `http://c3prog.local` (англійською / українською): вибір Wi-Fi, стан, кнопки «Перезапустити» і «Режим прошивки» для WT32, власна прошивка C3 (версія, час збірки, коміт, SHA-256) та її оновлення.

> Статус: зібрано (ESP-IDF 6.1). **Перевірено на залізі** (C3 0.3.1–0.4.5, звичайний esptool 4.8.1 / pyserial 3.5 у Windows 11): `flash_id`, `read_flash` і `write_flash` через RFC2217 (на 460800 реально близько 300 кбіт/с: 1,2 МБ за ~31 с), лог через `miniterm`, скидання RTS → EN, повторні підключення з очищенням буферів, `c3prog.local` через mDNS, сторінка C3; на 0.4.2 — сторож EN (WT32 повертається за 6–10 с після обірваного зʼєднання); на 0.4.3 монітор, що лише читає, не відвалюється (51 с без команд); на 0.4.5 наступний клієнт через 15–17 с після пастки з маршрутом, а другий клієнт чекає в черзі, не заважаючи першому. Ще не перевірено: запасний шлях через USB, дії кнопки BOOT і власне оновлення C3 через його сторінку.

## 1. Прошити C3 готовим бінарником

Файл: [`firmware/c3-programmer.bin`](firmware/c3-programmer.bin) — один образ, пишеться з адреси `0x0`.

**З браузера (Chrome/Edge, нічого не встановлювати):** https://espressif.github.io/esptool-js/ → *Connect* → вибрати порт C3 → *Flash Address* `0x0`, файл `c3-programmer.bin` → *Program*.

**Або esptool:**
```bash
pip install esptool
esptool.py --chip esp32c3 -p /dev/ttyACM0 write_flash 0x0 c3-programmer.bin    # Windows: -p COM5
```

Якщо C3 не видно як порт: утримуйте BOOT, натисніть RESET, відпустіть BOOT — і повторіть.

## 2. Підключити до Wi-Fi

1. Після прошивки C3 піднімає точку доступу **`C3prog-Setup-XXXX`** (відкрита). Світлодіод блимає подвійно.
2. Підключіться до неї телефоном — сторінка налаштування відкриється сама (якщо ні — http://192.168.4.1). Пароль сторінки — `12345678`; змініть його в розділі «Пароль сторінки». Перемикач EN / УКР (на формі входу і в заголовку) змінює мову сторінки.
3. Оберіть мережу, введіть пароль, за бажанням змініть імʼя пристрою → «Зберегти і перезапустити».
4. C3 підключиться до мережі; сторінка — `http://c3prog.local` (або IP з роутера). Світлодіод горить рівно.

Якщо збережена мережа недоступна 60 с, точка налаштування вмикається знову (C3 при цьому далі пробує підключитися).

## Оновлення прошивки C3 через сторінку (OTA)

Розділ «Прошивка» на сторінці: файл **`firmware/c3-programmer-ota.bin`** → «Оновити прошивку». Повний образ `c3-programmer.bin` (для адреси `0x0`) сторінка відхилить — він лише для прошивки кабелем.

- Перед записом перевіряється, що образ для цього чипа і цієї прошивки; після запису — цілісність.
- Флеш має два слоти (`ota_0`/`ota_1`, по 1,875 МБ); нова прошивка пишеться в неактивний, старий лишається.
- Після перезапуску нова прошивка **на перевірці 60 с**: якщо за цей час вона впаде або перезапуститься, завантажувач повертає попередню. Таблиця «Прошивка» покаже, яка версія реально працює, з часом збірки й комітом.
- Сесії не переживають перезапуск — сторінка попросить увійти знову.
- Перший раз прошивку з цією розміткою треба записати кабелем (повний образ з `0x0`); налаштування (NVS) при цьому зберігаються.

## Підключення до WT32

Схема і кроки першої прошивки: [`docs/WIRING_UA.md`](../../docs/WIRING_UA.md).

| C3 SuperMini | WT32-ETH01 | Примітка |
|---|---|---|
| GPIO4 (UART1 TX) | RXD (IO3) | |
| GPIO5 (UART1 RX) | TXD (IO1) | внутрішня підтяжка вгору на C3 |
| GPIO6 | EN | open-drain: лише тягне вниз або відпускає |
| GPIO7 | IO0 | open-drain; після старту WT32 завжди відпущений (IO0 = тактування Ethernet) |
| 5V | 5V | лише на столі; **не 3V3** |
| GND | GND | обовʼязково |

## Кнопка BOOT і світлодіод на C3

| Утримання | Дія |
|---|---|
| < 1 с | WT32 → режим прошивки |
| 1–5 с | перезапуск WT32 |
| 5–10 с | перезапуск самого C3 |
| ≥ 10 с | забути Wi-Fi і скинути пароль сторінки на `12345678` (C3 повертається в режим налаштування) |

Світлодіод: подвійне блимання — точка налаштування; 1 Гц — підключення до Wi-Fi; горить — готовий; мерехтить — обмін з WT32.

## Прошивка WT32 через Wi-Fi

```bash
esptool.py --chip esp32 -p rfc2217://c3prog.local:4000 flash_id
idf.py -p rfc2217://c3prog.local:4000 flash monitor
```

Лише монітор (без `idf.py`):
```bash
python -m serial.tools.miniterm --rts 0 --dtr 0 rfc2217://c3prog.local:4000 115200
```
`--rts 0 --dtr 0` обовʼязково: за замовчуванням pyserial піднімає RTS, і WT32 висить у скиданні.

Якщо `.local` не резолвиться (часто на Windows без Bonjour), використовуйте IP зі сторінки стану.

Якщо автоскидання по мережі не спрацьовує: на сторінці натисніть «Режим прошивки» (або коротко BOOT на C3), потім `esptool.py ... --before no_reset ...`.

## Прошивка WT32 через USB (запасний шлях)

USB C3 не передає швидкість і DTR/RTS, тому:
- лише `-b 115200`;
- `--before no_reset --after no_reset`: сигнали скидання з ПК скидали б сам C3, а не WT32.

```bash
# 1. «Режим прошивки» на сторінці або коротко BOOT на C3
cd build   # тека збірки прошивки WT32
esptool.py --chip esp32 -p /dev/ttyACM0 -b 115200 --before no_reset --after no_reset write_flash @flash_args
# 2. «Перезапустити» на сторінці або BOOT 1–5 с
```

Монітор: `python -m serial.tools.miniterm --dtr 0 --rts 0 /dev/ttyACM0 115200`
(`--dtr 0 --rts 0`, щоб не скинути C3).

## Відомі обмеження

- Один мережевий клієнт RFC2217 одночасно. Від 0.4.5 ще до чотирьох зʼєднань чекають у черзі; esptool/pyserial, що чекає, здається приблизно через 3 с з повідомленням «Remote does not seem to support RFC2217 or BINARY mode»: запустіть його знову, коли поточний клієнт відключиться.
- До 0.3.1 перший же запит очищення буфера від esptool/pyserial (`timeout while waiting for option 'purge'`) вішав потік з'єднання, і сервер після цього не приймав жодних клієнтів до перезапуску C3. Виправлено в 0.3.1: прошийте новий `c3-programmer.bin` через USB (або `-ota.bin` через сторінку).
- Якщо ноутбук зник посеред сесії (сон, обрив Wi-Fi), з'єднання може лишатися відкритим, доки TCP не здасться, і до того нові з'єднання не приймаються. Якщо в цей момент EN (RTS) було встановлено, WT32 теж лишається в скиданні. Тоді перезапустіть C3 (BOOT 5–10 с). Так було до 0.4.2: відтоді C3 помічає зниклий клієнт, закриває зʼєднання, відпускає EN і IO0 та приймає наступного клієнта. Від 0.4.3 після 10 с без нічого від клієнта C3 просить його відповісти (запит опції telnet, який pyserial одразу відхиляє) і закриває зʼєднання, якщо відповіді немає 5 с (`menuconfig` → *Drop an RFC2217 client…*); монітор, що лише читає, відповідає і лишається (перевірено на 0.4.3). Від 0.4.4 розрив жорсткий (RST) і робиться окремою задачею. 0.4.2 покладався лише на TCP keepalive (на папері теж ~15 с). На залізі (лог налагоджувальної збірки, 0.4.4) мертвий клієнт із пастки з маршрутом нижче зникає приблизно через 15 с після свого останнього пакета (першим його обриває TCP keepalive).
- Від 0.4.2 EN, який клієнт тримає довше 3 с без нових керівних запитів, відпускається разом з IO0, і це видно в лозі (`menuconfig` → *Release EN…*; esptool та idf.py тримають його ~100 мс). Побічний ефект: miniterm, запущений без `--rts 0`, більше не тримає WT32 у скиданні довше 3 с. Перевірено на 0.4.2 (пастка з маршрутом нижче): EN відпущено, WT32 і лінк повернулися за 6–10 с.
- **Пастка з маршрутом:** якщо ПК, на якому запущено esptool/miniterm, має ще й дротовий інтерфейс за WT32 (наприклад, коли ПК сам є пристроєм для перевірки), ОС може пустити зʼєднання RFC2217 через WT32 (у Windows метрика Ethernet 5 менша за 35 у Wi-Fi). Скидання через RTS тоді обриває те саме зʼєднання. На 0.4.0 і 0.4.1 WT32 після цього лишалася в скиданні, а C3 не приймав нових клієнтів до перезапуску (BOOT 5–10 с або перепідключення USB). Від 0.4.2 сторож EN повертає WT32 за 6–10 с, а мертвий клієнт закривається приблизно через 15 с. На 0.4.2–0.4.4 новий клієнт усе одно підключався лише через 31–34 с, а якщо пробувати знову кожні кілька секунд — більше ніж за хвилину: з чергою прийому на одне місце повторна спроба, що здалася, поки сервер був зайнятий, лишала в цьому місці напіввідкрите зʼєднання (SYN-RCVD: її сокет уже закрито, коли приходив SYN-ACK від C3, а брандмауер Windows не відповідає RST), lwIP тримав його ~18 с і відмовляв усім іншим, а наступна спроба робила те саме (видно в таблиці TCP lwIP у налагоджувальній збірці; на звичайній збірці те саме показують `clientFor`, `clientDrops` і `clientDroppedAgo` в `/api/status`). Від 0.4.5 черга на чотири місця: перевірено на залізі, наступний клієнт підключається через 15–17 с після скидання (три прогони, повторні спроби кожні 2,7–4 с), другий клієнт, поки підключено перший, чекає й отримує повідомлення вище, а першому це не заважає. Щоб уникнути пастки зовсім, привʼяжіть клієнт до іншого інтерфейсу або додайте маршрут до C3.
- Сторінка під паролем (за замовчуванням `12345678`), але сам порт RFC2217 (4000) — без пароля: будь-хто в тій самій мережі може прошити або скинути WT32. Для домашнього стола прийнятно.
- Точка налаштування відкрита (без пароля Wi-Fi); сторінка за нею — під паролем.
- Потужність Wi-Fi за замовчуванням знижена до 8,5 дБм — типове лікування проблем антени SuperMini. Якщо зв'язок слабкий, змініть у `menuconfig`.
- Лог самого C3 виводиться лише на UART0 (GPIO21), бо USB віддано під дані WT32.
